# UI review: notifications inbox

Branch `feat/notifications-ui` (bell, popover inbox, page findings from the drift monitor). Spec §8.4 review. A fresh
reviewer read spec §5 (5.1–5.7, all of it), reports/design-system.md (tokens, contrast table, icon registry), and the
make-interfaces-feel-better skill (SKILL.md and its four sibling files). Code read: `features/notifications/`
(`NotificationBell.tsx`, `Inbox.tsx`, `text.ts`, `useNotifications.ts`), the `.app-bell*` / `.app-inbox*` block at
the end of `theme/theme.css` (3737–3833), the four new keys in `ui/icons.ts`, the `AppShell.tsx` mount, and
`ui/toast.tsx`. Then I viewed every screenshot.

Screenshots in `docs/plan/reviews/ui/notifications/`. The PR's six, all at 1440×900 from
`e2e/screenshots-notifications.spec.ts`: unread, empty, many, loading, error, bell. The reviewer's seven captures plus `review-measurements.json`, from a
throwaway `e2e/zz-review-*.spec.ts` (deleted) on the same stubs: `review-bell-focus-1440` (bell reached by Tab),
`review-focus-row-1440` (row focused with arrow keys), `review-hover-read-1440` (hover on a read row),
`review-all-read-1440` (after Mark all read), `review-landing-mention-1440` (review screen after Enter on a mention),
`review-many-1280` (1280×800), `review-bell-99plus-1440` (150 unread). Keyboard traces, box sizes, computed colors,
the ARIA tree and per-row truncation are in `review-measurements.json`. All keyboard observations below were driven
with real key presses and read back from `document.activeElement`.

Verdict: **0 blockers, 6 should-fix, 10 nits.** The inbox works. Rows are domain sentences ("Dana Reyes requested
changes on CP-1038 · …"). The count is not a status color. Unread is marked three ways: dot, weight, and color.
Escape returns focus to the bell, and a 30 s poll that delivers a new row while you're arrowing through the list
keeps focus on the same row. Four of the should-fixes are about what happens around the list: where focus goes when
the popover opens, after Mark all read, and after opening a row, plus one color borrowed from the wrong status. The
other two are the truncation rule and the accessible names.

## Keep

- **The count isn't a status color.** `.app-bell-count` is inverse brand: `primary` text on `primary-content` (13.19:1
  per design-system's table), with a 1.5px `primary` ring that separates it from the glyph (`bell-1440.png`). That's
  right under §5.2: an unread count mixes kinds, so it isn't "act now". Using alert would also make every new
  assignment look like drift. It uses `tabular-nums`. The unread dot is navy too, and "unread" isn't a workflow
  status.
- **Read rows pass contrast.** Measured `.app-inbox-line` on read rows: `oklch(0.47 0.022 258)` = `muted`, which is
  6.72:1 on `base-100` (design-system). On hover the background is `base-content / 0.06` (`review-hover-read-1440.png`),
  still about 5.9:1 by the same math. Unread is marked by dot, weight (`font-medium` title) and color, never by color
  alone.
- **The glyphs follow §5.2a.** Decisions reuse their outcome's status glyph and tone (requested changes = amber
  ArrowUUpLeft, rejected = red XCircle, approved = green CheckCircle). Re-review is alert and uses
  `status.needs_rereview`. The drift row reuses `severity.blocking` exactly as Placements does. The new keys are
  distinct glyphs: `icons.test.ts` passes (`vitest run src/ui/icons.test.ts src/features/notifications`: 3 files,
  29 tests). ClockCountdown (expiring) is clearly apart from CalendarX (expired), and Checks (mark all read) from
  Check (approve). No sparkle, emoji, gradient or shadowed card (§5.6). The popover has the one overlay shadow.
- **Copy uses the domain terms** (§5.4): "requested changes on", "needs re-review · offer terms changed", "Approval
  for CP-988 · … expires Nov 23", "approved … with edits". The CP key is mono, and nothing is chatty.
- **Keyboard inside the list works** (measured): Arrow keys, Home/End, typeahead ("S" → the Sam Okafor row), and the
  focus ring is a 2px navy inset on the row (`review-focus-row-1440.png`). Escape closes and returns focus to the
  bell. A click outside closes it. When a poll delivered a new row while a row was focused, focus stayed on the same
  row (`pollWhileOpen`). The bell's focus ring on the navy bar is visible (`review-bell-focus-1440.png`).
- **Rows are good targets.** The whole 36px row (`row` token) is the target, and the age is right-aligned with
  `tabular-nums` and gives the absolute time as its title and its spoken name. Mention → Comments on v2 resolves
  (`/items/1042?tab=comments&v=2`, measured). Drift → Details comes from `notificationLink` in code, but it wasn't
  driven here.
- **Read receipts are optimistic and roll back** (§5.7 low-stakes). Mark all read toasts on failure, a single read
  rolls back silently, and the bell's mutations live outside the popover, so a click survives the popover closing.

## Fixture and method notes (not findings)

- The red "Couldn't load queue counts" / "Couldn't load saved views" banners in `error-1440.png` come from `stubApi`
  lacking those endpoints in that mode, not from this PR. The same goes for the stat skeletons in the queue header.
- The make-interfaces-feel-better checklist items with nothing to report: the popover fades on `opacity` only
  (`.app-popover` `transition-property: opacity`, 100ms), there's no `transition: all`, no `will-change`, and the
  numbers use `tabular-nums`. The concentric-radius rule is waived under the 6px ceiling as in prior reviews
  (`rounded-lg` 6px popover, `p-1`, `rounded-md` 4px rows). The 40px hit-area rule is waived as in design-system.md:
  the bell is 32×32 like every topbar button, and Mark all read is 117×28.
- The 1280×800 capture did not open the assistant panel. Its only finding is that the popover stays a fixed 512px
  and fits (list `clientHeight` = `scrollHeight` = 640).
